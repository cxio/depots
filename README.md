# 数据驿站（Depots）

在传统的数据分享应用里，针对想要的数据，用户可以根据数据的索引ID，从拥有数据的多个节点那里获取。

拥有数据的用户是零散的，有的用户即便拥有数据，也不一定在线或开启数据分享。用户与用户之间没有关联，分享是一种极其松散的逻辑。

数据的重要性不言而喻，但在开放领域，长期的数据保存和分享可能是一个问题。


## 开放式存储

数据驿站是一个开放的数据存储&分享网络，但与 IPFS/Filecoin 的严肃/严格逻辑不同，这里采用松散和自由的模式——任意节点都可以成为存储者和广播探测者。

因为缺乏严谨的经济激励，本项目尚属一个实验：尝试为某些公共开放的数据存储和检索提供服务。


### 紧缺性感知

网络节点对数据的请求通过广播扩散，如果请求每转播一次就跳数加一，则通过跳数的大小，节点可以感知请求广播的距离。总体上来说，广播的距离越远，说明数据越稀缺，节点根据历史情况综合评估数据的稀缺性，决定是否启动补充存储。

评估数据在全网的紧缺性是一项复杂的工作，详见 [存储策略](./docs/conception/存储策略.md)。数据感知设计详见 [数据感知](./docs/conception/数据感知.md)。


### 数据心跳

松散的协作方式很难保证数据的完备性，如果某些数据请求很少，在长期的*淡忘*之下，它们很可能就会消失。因此就需要某种措施，来保证数据请求的广泛性，这就是「数据心跳」。

数据心跳是一些公益节点通过某些数据索引/目录，向网络发送间歇性的探测请求，触发局部甚至整个网络对目标数据的紧缺性感知、补充存储，从而维护数据的持久可得性。

区块链附件有确定性的索引，因此完备性不是问题。但本系统是开放性的，探测包可以由任意节点发出，因此任何组织和个人，都可以根据自身需要，用自己的文件清单进行探测，维持心跳。

> **提示：**
> 发起心跳的探测节点最好在地理上均衡分布，或有意控制连接池节点在地理上合理分布。

## 备注

随机图蒙特卡洛模拟（Opus5.5）显示数据感知中「跳数/距离不足以表达稀缺性」，因为单条数据的密度（几十个存储点）与网络节点数规模（几十万）不是一个数量级别，基本上无法实现感知。

AI 提议方案：
1. **心跳节点直接数副本**：用现有的询问机制数回复数（最多 128 条）。先用低跳数，数量不够再加大，以节省流量。
2. **精确招募**：测出还缺 k 份后，发出一条带 k 的招募消息，沿 k 条二三十跳的短随机游走送到近似均匀随机的节点。

理论上可解，但心跳节点不再轻量，与初始「心跳节点只负责发探测」的理念相去甚远。且当前已有不少存储网络项目在运行，故暂停本项目。

> **后期方向：**
> 数据「驿站」可能应当是一个微中心的逻辑，组合使用已有的存储网络，作为一个入口存在。
> 当然，不同的驿站可以相互沟通，组成一个「微中心化」的网络。
