# 档案存储

本存储方案采用本地文件系统，仅支持P2P文件分享客户端。

原则上，存档文件的大小没有限制，但还是不支持大于**64GB**的文件。


## 存储策略

三项措施：**策略函数**、**白名单**、**黑名单**。


### 策略函数

由存储节点自己编写（Lua 或 Go），在数据查询无果时触发（在黑白名单之后）。

函数声明：`func(id []byte, size, jumps int) bool`，其中：

- `id` 为数据索引，最长256字节。
- `size` 为数据大小，以字节为单位。
- `jumps` 为查询跳数，小于16（4Bit位上限）。

如果函数返回 true，则表示需要补充存储，否则忽略。


### 白名单

有些数据可能是节点想无条件保留的，这就是白名单的逻辑。

白名单的目标ID并不是数据ID，而是一个随机种子（用户可配置）与数据ID的串连哈希。这是隐私保护的考虑，避免被简单窥探。


### 黑名单

虽然我们期望无差别的随机存储，这对数据的均衡分布有利。但肯定有用户不希望存储某些东西，这就是黑名单。

黑名单的ID规则与白名单一样，也有哈希遮蔽的处理。


### 优先级

白名单先于黑名单检查。

如果某一目标同时存在于黑名单和白名单中，则白名单有效。

其次，黑名单优于策略函数，如果某一目标已经存在于黑名单中，则不会再执行策略函数判断。

优先级： *白名单 > 黑名单 > 策略函数*

> **提示：**
> 如果有大量的目标需要进入黑白名单，可能用数据库来管理会更好（如 SQLite）。



## 本地存储

驿站节点在启动初期会构造一个数据ID的判断池（如布隆过滤器），当询问的请求到达时，会先判断数据的有无。


### 文档元信息

存档的数据除了文档本身外，还会有一个元信息文件，包含了对文档基本信息的记录。

通常有如下条目：

- 文件：文档文件名，含扩展名（如 .tar, .zip）
- 类型：实际内容的 MIME 类型（HTML）
- 标题：文档的名称（主标题）
- 概要：文档的内容摘要、大纲
- 大小：打包文档的大小（bytes），通常自动检查而来
- 语言：内容所属语种，可多语种并列（首项为主）
- 作者：文档的原始作者，多位并列
- 创建时间：文档原始创建时的时间，可选
- 版权：文档的原版权声明，可选。公共域内容可能无明确版权
- 指纹：打包文档的哈希（`SHA3-512`）摘要
- 清单：包内文件名列表，可选
- 额外补充：特定档案可能有的额外信息补充（`JSON-Object`），可选


### 存档路径

文档的哈希指纹也称为文档ID（`DID`）。

存档采用四层目录结构，按文档ID的3字节序列分组，末端为文档ID的16字节片段。

```go
2026/                               // 年度（存档时间），友好
    DID:1_ff/                       // 一级：文档ID首字节16进制表达，大写
        DID:2_ff/                   // 二级：ID次字节16进制表达，小写，前置0x
            DID:3_ff/               // 三级：ID第三字节16进制表达，3位十进制
                DID[:16]/           // 存档目录，ID序列前段
                    [file].xxx      // 存档文件，名称与.meta内「文件」字段相同
                    info.meta       // 文档元信息，通常为SON格式
                documents.list      // 各存档 "ID[:4] => Title|File" 对应清单（人工友好）
                                    // ID[0:4]长度可灵活处理，最短不重复即可
```

三层256分组最多可以离散*16M*区隔，且顶层按年度分隔，便于管理。


### 固化存储

通常来说，存档不可修改，甚至删除都不应有，所以长期保存是其基本逻辑。这能带来一些优势：

- 方便优化，以提高存储和检索效率。
- 单次只写易于采用廉价高容量存储介质，便于大规模存档。
- 易于做安全性防范，除非物理破坏，很难数据误操作（如覆盖写入）。



## 存储激励

如果节点存储的是区块链里的附件，由于区块链可以提供代币回报，所以此时的存储是有动机的。

但对于非区块链类应用，存储的驱动力可能是个问题。

P2P文件分享式存储近似于公共域逻辑，如果文档大部分为开放版权，出于对数据价值的挖掘，或许存储动机的问题可以解决。


### 存储应用

在手机拍摄便捷的自媒体时代，很多人的数据其实是愿意分享的。如果有一个数据分享应用：

- 把自己的数据交给别人保存。因为是随机的冗余式存储，所以很难丢失。
- 自己存储别人的数据。因为是别人的，所以其实没那么在意是否丢失。心态是轻松点，但随机冗余提供了保障。

这或许是一个不错的分享模式，人人为我，我为人人。
