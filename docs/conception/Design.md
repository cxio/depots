# 详细设计

> **前提：**
> - 节点需要事先知道自身的 NAT 类型。
> - 出于隐私保护，数据包不附带明文位置信息（IP）。

伪代码格式约定：

- `(n)` 占用字节数，即 n bytes。
- `[n]` 占用比特位数，即 n bits。

部分字节数和比特位数只是一个示意值，主要表达一种设计意图。


## 数据询问

应用节点创建「询问」消息包，其中包含目标数据标识，以及起始跳数。

数据询问遵循跳数递减规则，最高默认值**7**，每跳减一，减至**0**时终止转播。用户也可以设置更低的起跳数，但广播范围也会因此而缩减。

在广播的路径中，拥有该数据的节点回复并停止转播，而没有该数据的节点将请求跳数减一后续传。


### 询问包

```go
(2)     Ver:        版本号。
(8)     ID:         标识本次询问，用于回复包中对应其源请求。
(8)     Timestamp:  询问时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     DataKey:    数据键（≤32），可为前缀片段。
(~)     Size:       数据大小（字节数，0 值表示未知或忽略）。
(~)     HPKE:       加密用公钥素材：Hybrid Public Key Encryption
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Proof:      工作量证明。会绑定以上字段信息，算法见下文。
(1)     Hops:       剩余跳数，初始值 ≤7，最低到0。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下为单向哈希链认证段，防止 Hops 回撤：
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(20)    WayOn:      路途哈希，下一步哈希源。
                    接收者：WayOn = Hash( WayOn )
(20)    WayEnd:     跳数终点哈希值。
                    验证：Hash( WayOn )^Hops+1 == WayEnd
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

询问包为明文。但节点之间的通讯是加密的，避免第三方窥探。

广播的每跳扩散数为 `≤4`。节点可根据自身情况选择更少的扩散数，但只能低不能高，避免形成消息洪泛。

> **实现：**
> 在询问包的转播扩散中，中转节点应记住查询来源，因为回复包需要原路径返回。

节点不会转播重复的询问包，重复判定可用 Proof 字段值。也不会转播时间戳太旧（**2**分钟误差）的询问包。


#### 单向哈希链

询问包携带 `20+20` 共 40 字节的单向哈希链认证数据，避免攻击者调高剩余跳数，实施放大攻击。

```go
// 询问者初始 WayOn
// Seed 为询问者私有种子
// Hash 采用 BLAKE3 截取结果前 20 字节。
WayOn = Hash( Proof || Hops || Seed )

// 每一跳 WayOn
// 计算上级发来的 WayOn，写入中转询问包
WayOn = Hash( WayOn )

// 验证：
// 根据剩余跳数迭代计算
if Hops > 7 {
    return false
}
tmpOn = WayOn
for i range Hops+1 {
    tmpOn = Hash( tmpOn )
}
return tmpOn == WayEnd
```

初始跳数并不固定为**7**，询问者可以根据自身需求（隐私）调整，但最大值为**7**。


### 阻滞器

节点可以任意构造目标键进行查询，如果目标是虚假的（没有真实数据对应），则消息会广播很远很宽，消耗带宽和资源。

这可能成为一种攻击方式，因此设计如下规则。

针对每一个连接的对端：

- **计数限制**：询问量上限为 `15`，超限后即暂停接受新请求。**注**：中转询问也是询问。
- **机会回归**：每收到一个回复（非重复），计数减 `1`。这可使得该端点的询问/中转机会回归。
- **重置计数**：计数限制持续 `20` 秒，时间结束后重置为0，及时消除误判和阻滞。

这样，虚假的数据请求会被抑制在 `0.75次/秒` 的频率，且每个请求都要付出工作量。而正常的请求则问题不大。


### 工作量

每个询问都需要完成工作量计算，算法如下（示意）。

**通用部分：**

```go
import "github.com/cxio/equix-cgo/puzz"

// 命中率：6%
// 固定配置，针对当前流行PC，单核约 500 毫秒成本。
threshold := puzz.FromProbability(0.06)

// 基础信息：
// 询问包里的不可变字段值。
// domainTag  查询用域标识：depots:Query@v1
baseInfo := domainTag ||
            Ver ||
            ID ||
            Timestamp ||
            DataKey ||
            Size ||
            HPKE
```

**每查询求解：**

```go
// 求解：
// Hash256  256位哈希算法：BLAKE3
// Rand16   工作量求解者寻找的16字节随机数，会作为证明的后半段
// solution 一个合法解，2*8 = 16字节
var Rand16, solution
for {
    // 每轮生成新的 Rand16
    Rand16 = ...
    solution, _ := threshold.Try( Hash256(baseInfo || Rand16) )
    if solution != nil {
        break
    }
}
Proof := solution || Rand16
```

**中转/末端验证：**

```go
// 验证解：
// 效率极高，适配现代PC，单核约 30~40 微秒。
Rand16 := Proof[16:]
solution := Proof[:16]
seed := Hash256( baseInfo || Rand16 )

return threshold.Accept( seed, solution )
```

中转节点首先验证询问包的工作量，然后检查自身是否拥有目标数据。


### 响应回复

如果节点拥有目标数据，创建*回复包*响应。否则检查跳数是否非零，是则将询问包跳数减一后转播，否则停止。

返回的回复包会按询问广播的原路径逆向回传，逐级收敛回到查询者。

> **设计：**
> 原路回传既可以避免信息洪泛，也可以让询问者不必公开自己的位置（IP）。

如果数据源节点是受限 NAT 类型（`RC|P-RC|Sym-Like`），通常需要借助于 STUN2 服务子网协助打洞互连，所以会包含其所连接的 STUN2 子网服务节点的身份ID。


### 回复包

```go
(2)     Ver:        版本号。
(8)     ID:         原询问包中的ID，用于上级对应请求源。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Cipher:     回复者的协商密文，封装了共享密钥。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
注：以下信息会用共享密钥加密
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
[4]     HopEnd:     询问包抵达回复者节点时的跳数。
(8)     Timestamp:  回复包的时间戳。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(n)     DataKey:    目标数据键，可以比询问包中的键更长，但前段必须相同。
(32)    BaseID:     回复者在基网中的身份ID。
(32)    PunchID:    打洞协助节点的身份ID（STUN2 子网服务器），可选。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra:      额外信息。可选，≤127 字节。
                    用例：
                    如果需要连接 STUN2 服务子网，可以是节点的身份识别号，
                    询问者借助于此识别号在 STUN2 子网中匹配它。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```


### 回传策略

- 每个中转节点向上回传的回复包最多**16**个。这是强约束。
- 对同一下级节点回传的包通常只取其中**4**个包。这是松约定，主要为强化随机性，节点可自行权衡处理。

这样，对于发送询问的初始节点来说，如果它连接了8个节点发送询问，最多可收到128个回复（数据源不会对相同 Proof 查询重复响应）。



## 心跳探测

探测数据的存在性是一种特殊的请求，它不需要拥有数据的节点回复，只要它们停止转播即可。

与询问包不同，探测包的起始跳数为零，遵循跳数**递增**的策略，最大跳数截止于**15**（当前设计值）。节点的转播扩散数与查询规则相同，对重复的探测包也会简单忽略。

任意节点都可以发出探测包，但需要付出工作量。对于普通节点来说，这没有什么益处。心跳探测是一些愿意付出的公益节点的事。

> **设计：**
> 探测包没有签名认证机制，因此只能用工作量来对抗可能的攻击。
> 同时工作量也是探测频率的限制器。


### 探测包

```go
(2)     Ver:        版本号。
(8)     Timestamp:  起始时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    DataKey:    数据键。需为完整32字节长。
(~)     MetaInfo:   数据元信息（可选）：
                    Kind:     种类，2字节（1+1）
                    Title:    数据名称/标题，≤200 字节
                    Size:     数据大小（字节数）
                    License:  许可证名称，≤64 字节
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Proof:      工作量证明。会绑定以上字段信息，算法见下。
(1)     HopCnt:     跳数累计，初始值0，最高到15。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下单向哈希链约束 HopCnt 回调：
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(20)    WayOn:      路途哈希，下一步哈希源。
(20)    WayEnd:     跳数终点哈希值。
                    验证：Hash( WayOn )^16-HopCnt == WayEnd
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

探测包为明文，无加密。数据元信息为可选，全包合计字节数不超过 400 bytes。

> **设计：**
> 数据元信息是存储者评估偏好的必要参考，但探测包广播太自由，必须轻量。
> 因此取消了 Summary 字段，代之以较宽容量的标题（≤200 字节）。


### 探测包工作量

探测包的工作量设计与询问包类似，只是绑定的字段不同。

```go
// 基础信息：
// 探测包里的不可变字段值。
// domainTag  查询用域标识：depots:Probing@v1
baseInfo := domainTag ||
            Ver ||
            Timestamp ||
            DataKey ||
            MetaInfo
```

其它求解和工作量验证逻辑与「询问包」章节相同。


### 补充储备

如果节点根据存储策略判断需要存储时，即可构建询问包，向网络发起广播询问。

因为询问的回复包中包含终点跳数，所以节点也可以计算出到数据源的距离，如果很近，且收到很多回复，则表示该数据的存储冗余度可能比较大。节点可以尝试请求局部数据片，验证后确定是否需要补充存储。

> **注意：**
> 攻击者可以针对目标数据，假装自己有存储，欺骗询问者。

新数据的发布也可以通过探测包广播间接完成：有需求的节点发布询问，发布者充当数据源。但因为数据源单一，所以询问会花费较多的时间。



## 数据发布

新数据的发布采用专用的**发布包**请求，结构与询问包类似，但包含数据的元信息（非可选）。


### 发布包

```go
(2)     Ver:        版本号。
(8)     ID:         标识本次发布，用于回复包中对应其源请求。
(8)     Timestamp:  发布时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    DataKey:    数据键（完整）。
(~)     MetaInfo:   数据元信息：
                    Kind:     数据类别
                    Title:    数据名称/标题，≤127 字节
                    Summary:  内容摘要。≤500 字节
                    Size:     数据大小（字节数）
                    License:  许可证名称，≤64 字节
(~)     HPKE:       加密用公钥素材。
(~)     Deposit:    寄存激励（可选）：
                    Name:     代币名称（区块链，如 Bitcoin），≤32 字节
                    Amount:   预期支付数量（报价）
                    Payfrom:  支付地址。仅参考用途，实际可能不同，≤64 字节
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Proof:      工作量证明。
(1)     Hops:       剩余跳数，初始值 ≤7，最低到0。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下为单向哈希链约束（同询问包）：
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(20)    WayOn:      路途哈希，下一步哈希源。
(20)    WayEnd:     跳数终点哈希值。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

发布包包含可选的区块链代币激励（通常为到期兑付合约）条件。

发布包与询问包的逻辑也类似，有原路回传的响应回复。因此也遵循限制发送频率的「阻滞器」策略，以及相同的不重复原则。


### 发布包工作量

发布包的工作量与询问包类似，只是绑定字段不同，难度相同。

```go
// 基础信息：
// 发布包里的不可变字段值。
// domainTag  查询用域标识：depots:Publish@v1
baseInfo := domainTag ||
            Ver ||
            ID ||
            Timestamp ||
            DataKey ||
            MetaInfo ||
            HPKE ||
            Deposit
```

其它求解和工作量验证逻辑与「询问包」章节相同。


### 关于寄存激励

与 Filecoin 严格的存储验证/激励不同，这是一种松散的自由合约形式。发布者向网络发布数据请求外部存储，有意愿者回应，双方联系后协商寄存合约。合约通常是一种「到期兑付」脚本，也不限制代币类型。

注意，这里只提供基本报价信息的传送，不负责任何实际的交易或约束。

因为链上的附件通常只保存附件ID，实际上需要额外的存储，所以这里提供一种初始报价信息的传送是必要的。


### 受托回复

发布广播路径上的节点评估发布包，如果愿意接受存储委托，即可构建*受托包*响应。

```go
(4)     Ver:        版本号。
(8)     ID:         原发布包中的ID，用于上级对应请求源。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Cipher:     受托者的协商密文，封装了共享密钥。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
注：以下信息会用共享密钥加密
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
[4]     HopEnd:     发布包抵达受托者节点时的跳数。
(8)     Timestamp:  回复包的时间戳。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    DataKey:    发布数据键。
(32)    BaseID:     受托者在基网中的身份ID。
(32)    PunchID:    打洞协助节点的身份ID（STUN2 子网服务器），可选。
(~)     Bargain:    受托议价（可选）：
                    Name:       代币名称，可与 Deposit.Name 不同，≤32 字节
                    Amount:     期望支付数量
                    Receiver:   收款地址。仅参考，实际协商可能不同。≤64 字节
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra:      额外信息。可选，≤127 字节。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

发布包/受托包中的代币名称和金额只是一种意向表达，最终结果取决于发布者对受托回复的评估：是否会进一步联系协商。



## 数据传输

### 获取信息

询问者收到回复后，解密获取相关信息。

- BaseID 是数据源节点在基网的身份ID，因此可以通过基网获取对端的联系信息（IP:Port、SPKI、ECHConfig、NATT 等）。
- PunchID 如果回复者是 NAT 内网节点，此ID即为其所连 STUN2 服务子网的服务节点ID。然后就可以请求该节点进行 UDP 打洞协助。

> **提示：**
> 节点的身份ID是跨应用一致的。基网 NodeID 只绑定节点的 IP，不含端口。
> STUN2 服务子网的节点也会连接基网，因此也可以从基网通过其身份ID（即 PunchID）找到。


### 传输数据

询问者找到数据源节点后，即可知道其 NAT 类型，以及可能需要的应用专属说明（Extra），然后就可以决定采用什么连接方式，传输数据。



## 安全性

### 末端延时

对于某些数据，可能有人不愿意它们被分享，因此大量部署监控节点，发现相关请求后立即响应，占据原路回传的头部位置，阻止真实回应。

因此这里设计这一机制：

- 对于每一个询问目标，节点会记录它的时间戳。
- 当一个询问目标的回复返回时，返回时间必须与询问时间有一个必要的差距。比如 `2~3` 秒。

这样，对于快速返回虚假回复的攻击者来说，它们的回复会被上级节点延时回传，从而失去优势。

这种末端延时不会影响中间层级的回传效率，因为正向转播时时间已经记录，逆向回传的延时要求已经被末端节点的直接上级完成了。

> **注记：**
> 2~3秒的延时主要参考*真实数据源查询自身数据*需要的时间估算。

这样，如果攻击者想要完全阻断询问回复的抵达，就需要部署*十分充足*的节点或针对特定询问者围堵才能完成。



## 项目边界

- 节点发现由 [基网](https://github.com/cxio/p2p) 实现，驿站节点可以通过基网找到对方。节点ID是跨应用一致的。
- 提供打洞协助的 [STUN2 P2P 网络](https://github.com/cxio/stun2p) 是基网的一个服务子网，也可以通过基网寻址。
