# 数据驿站详细设计

## 基本约定

- 节点需要事先知道自身的 NAT 类型。
- 出于隐私保护，数据包不附带明文位置信息（IP）。

伪代码用 Go 语言高亮，主要为视觉友好，非严格的 Go 语法。其中：

- `(n)` 占用字节数，即 n bytes。
- `[n]` 占用比特位数，即 n bits。
- `(~)` 表示占用不定数量字节数。

字节数和比特位数通常也只是一个示意值，主要表达一种设计意图。


## 数据标识

检索数据的 `DataKey` 就是存储文档里的分片哈希树根 `TID`。采用分片树根而不是数据字节本身的哈希摘要，可获得一种灵活性：用户可以通过*改变分片策略来变化索引键*。

询问可以使用键前缀（`DataKey` 前段局部），以获得某种隐私保护。但回复里需包含完整键（前段一致）。探测、发布和补存都使用完整 TID。

> **设计：**
> 文档数据本身使用 `SHA3-512` 摘要，只在本地元信息里，不参与检索。


## 数据询问

应用节点创建「询问」消息包，其中包含目标数据标识、加密凭证以及起始跳数。

询问广播的扩散数为**4**，跳数遵循递减策略，最高默认**7**，每跳减一，至**0**时终止转播。用户也可以设置更低的起跳数，以获得某种隐私性。

理想情况下，单个首跳节点（`Hops=7`）能向下扩散至 `16384` 个节点，与前段路径节点合计共 `21845`。

> **实现：**
> 节点收到高跳数（`7,6`）时，需根据概率来决定是否递减：
> - **递减**：按正常的 4 节点扩散率正常传播。
> - **不减**：仅向下转播一个节点，维持单路径形态。

节点的初始连接邻居从基网里搜寻（*基网为一通用节点发现网络*），之后的连接池则由驿站节点之间自行维护。


### 询问包

```go
(2)     Ver:        版本号。
(8)     ID:         标识本次询问，用于回复包中对应其源请求。
(8)     Timestamp:  询问时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     DataKey:    数据键（≤32）。完整 TID 或局部前缀（不能为零）。
(~)     Size:       数据大小（字节数，0 值表示未知或忽略）。
(~)     HPKE:       算法标识 + 变长公钥。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Proof:      工作量证明。绑定下面的 WayEnd，以及分隔线以上的字段。
(1)     Hops:       剩余跳数，初始值 ≤7，最低到 0。逐跳改变，不进入证明。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下单向哈希链防止剩余跳数被抬高：
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(20)    WayOn:      路途哈希。逐跳改变，不进入证明。
(20)    WayEnd:     跳数终点。整路不变，必须进入证明。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

询问包为明文。但节点之间的通讯是加密的，避免第三方窥探。

**基本规则：**

- 时间戳与本地时间相差超过 `±2 分钟` 的包会被丢弃。
- 重复的询问包不转发，判定重复用 `Proof`。可能设置条数上限，保新去旧。

这些基本规则也适用于后面的 *发布包* 和 [数据感知](数据感知.md) 里的 *探测包*。


### 单向哈希链

询问包携带 40 字节的单向哈希链，避免中继把剩余跳数改大、把广播拉长。

```go
// 源站。每次发包使用新的 32 字节 Seed，种子不外传。
WayOn = Hash(Seed)
WayEnd = WayOn
for i range Hops+1 {
    WayEnd = Hash(WayEnd)
}

// 接收方先验证，再决定回复或转发。
if Hops > 7 {
    return false
}
tmpOn = WayOn
for i range Hops+1 {
    tmpOn = Hash(tmpOn)
}
if tmpOn != WayEnd {
    return false
}

// Hops == 0：停止。否则转发前只走一步。
if Hops == 0 {
    return
}
Hops = Hops - 1
WayOn = Hash(WayOn)
```

初始跳数并不固定为 **7**，询问者可以根据自身隐私需求调整，但最大值为 **7**。

终点会绑定到 Proof，中继可以在本地把链多走几步再转发（剩余跳数更小，广播更短），但无法换一条更长的链来实施放大。


### 阻滞器

节点可以任意构造目标键进行查询，如果目标是虚假的（没有真实数据对应），则消息会广播很远很宽，消耗带宽和资源。

这可能成为一种攻击方式，因此设计如下规则。

针对每一个连接的对端：

- **计数限制**：询问包上限 `10`（按 `Proof` 区分），超限后即暂停接受对端的新询问请求。
- **机会回归**：每收到一个询问包的有效回复则减 `1`（按 `Proof` 区分冲抵），这使得中转询问的机会回归。
- **重置计数**：计数持续 `15` 秒，时间结束后重置为 0，及时消除误判和阻滞。

这样，虚假的数据请求会被抑制在约 `1.5s/次` 的频率，且每个请求都要付出工作量。而正常的请求则问题不大。

> **实现：**
> 中继需按入站邻居公平分配出站配额，避免转发虚假询问导致自身严重受限。
> 上限**10**是逻辑上的稳定值，具体编码可考虑用令牌桶来实施（桶深可为 30）。


### 工作量

每个询问都需要完成工作量计算，算法如下（示意）。

**通用部分：**

```go
import "github.com/cxio/equix-cgo/puzz"

// 命中率：6%
// 按当前普通 PC 标定，单核约 500 毫秒。
// 这是一个统一的固定配置，不可修改。否则不同客户端无法验证彼此。
threshold := puzz.FromProbability(0.06)

// 不可变字段。不含 Hops 与 WayOn。
// domainTag 查询包域标识：depots:Query@v1
baseInfo := domainTag ||
            Ver ||
            ID ||
            Timestamp ||
            DataKey ||
            Size ||
            HPKE ||
            WayEnd
```

**每查询求解：**

```go
// 求解：
// Hash256  哈希算法：SHA-256
// Rand16   工作量求解者寻找的16字节随机数，会作为证明的后半段
// solution 一个合法解，2*8 = 16字节
var Rand16, solution
for {
    // 每轮生成新的 Rand16
    Rand16 = ...
    solution, _ := threshold.Try( Hash256(baseInfo || Rand16) )
    if solution != nil {
        break
    }
}
Proof := solution || Rand16
```

**中转/末端验证：**

```go
// 验证解：
// 效率极高，适配现代PC，单核约 30~40 微秒。
Rand16 := Proof[16:]
solution := Proof[:16]
seed := Hash256( baseInfo || Rand16 )

return threshold.Accept( seed, solution )
```

中转节点先检查时间窗、工作量和哈希链，再看自己有没有目标数据。


### 响应回复

如果节点拥有目标数据，创建*回复包*响应。否则在跳数非零时，把跳数减一、`WayOn` 哈希一次后再转播。

返回的回复包会按询问广播的原路径逆向回传，逐级收敛回到查询者。

> **设计：**
> 原路回传既可以避免信息洪泛，也可以让询问者不必公开自己的位置（IP）。

如果数据源节点是受限 NAT 类型（`RC|P-RC`），就需要借助于 STUN2 服务子网协助打洞互连，所以会包含其所连接的 STUN2 子网服务节点的身份ID。


### 回复包

```go
(2)     Ver:        版本号。
(8)     ID:         原询问包中的ID，用于匹配上级来源。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Cipher:     用询问包里的 HPKE 公钥封装。
                    关联数据含询问 ID、Proof、WayOn、HopEnd。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
注：以下信息会用共享密钥加密
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(8)     Timestamp:  回复包的时间戳。
(1)     HopEnd:     抵达时的剩余跳数。
(32)    BaseToken:  基网联系口令。
                    当节点去基网中搜寻 BaseID 并连接时与对方核对，
                    通过即确认对端为当前回复者。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    DataKey:    完整 TID。
(32)    BaseID:     回复者在基网中的身份ID。
(32)    PunchID:    打洞协助节点的身份ID（STUN2 子网服务器），可选。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra:      额外信息。可选，≤127 字节。
                    用例：
                    如果需要连接 STUN2 服务子网，可以是节点的身份识别号，
                    询问者借助于此识别号在 STUN2 子网中匹配它。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

询问者解密提取信息，用 `BaseID` 在基网中搜索数据源节点，然后连接获取数据。注意此时 `DataKey` 已是完整 TID，便于询问者核对真实目标。

> **设计：**
> `HopEnd` 放在密文里，避免回复者暴露位置。回传按ID对应即可，无需再验路径。


### 回传策略

总则（强约束）：

- 每个中转节点最多向上回传 **16** 个回复包。
- 每个下级节点的回复最多取 **5** 条，以获得路径多样性。

中转节点对下级节点的回复包筛选：

- 如果还在延时期内（见下文「末端延时」），则等待汇聚，到点后随机抽选（每节点回复依然不能超过5个）。
- 如果延时期已过，则先到的回复先回传。但最终向上回传的总包数不超过16个。

这样，路径近的回复会先抵达，远的会被丢掉。排除攻击时的情形，这算是一种自然优化。

假设询问者连接了 8 个节点来发询问，可最多收到 128 个回复（数据源不会对相同 Proof 查询重复响应），理论上，这相当充足了。



## 数据发布

新数据的发布采用专用的**发布包**请求，结构与询问包类似，但包含数据的元信息。其它规则如扩散率、哈希链、时间窗、去重等都与询问包相同。

`Deposit` 与受托回复里的 `Bargain` 只是报价捎带，本协议不涉及其交互逻辑（应用自身业务）。


### 发布包

```go
(2)     Ver:        版本号。
(8)     ID:         标识本次发布，用于回复包中对应其源请求。
(8)     Timestamp:  发布时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    DataKey:    完整 TID。
(~)     MetaInfo:   数据元信息：
                    Kind:     种类，2字节（1+1）
                    Title:    数据名称/标题，≤127 字节
                    Summary:  内容摘要。≤500 字节
                    Size:     数据大小（字节数）
                    License:  许可证名称，≤64 字节
(~)     HPKE:       算法标识 + 变长公钥。
(~)     Deposit:    寄存激励（可选）：
                    Name:     代币名称（区块链，如 Bitcoin），≤32 字节
                    Amount:   预期支付数量（报价）
                    Payfrom:  支付地址。仅参考用途，实际可能不同，≤64 字节
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Proof:      工作量证明。绑定 WayEnd 以及以上字段。
(1)     Hops:       剩余跳数，初始值 ≤7，最低到 0。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下为单向哈希链（算法同询问包）：
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(20)    WayOn:      路途哈希。
(20)    WayEnd:     跳数终点。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

发布包包含可选的区块链代币激励（通常为到期兑付合约）条件。发布包也有回复，因此也适用「阻滞器」机制。


### 发布包工作量

发布包的工作量与询问包类似，只是绑定字段不同，难度相同。

```go
// 基础信息：
// 发布包里的不可变字段值。
// domainTag  发布用域标识：depots:Publish@v1
baseInfo := domainTag ||
            Ver ||
            ID ||
            Timestamp ||
            DataKey ||
            MetaInfo ||
            HPKE ||
            Deposit ||
            WayEnd
```

其它求解和工作量验证逻辑与「询问包」章节相同。源站同样先确定 `WayEnd`，再求解 Proof。


### 关于寄存激励

与 Filecoin 严格的存储验证/激励不同，这是一种松散的自由合约形式。

发布者向网络发布数据元信息，请求外部存储。有意愿者回应，双方联系后协商寄存合约。合约通常是一种「到期兑付」脚本。发布者可指定其期望的任意代币类型，本协议不作任何预设。

注意这里只是提供基本报价信息的传送，不负责任何实际的交易或约束。

因为链上的附件通常只保存附件的ID，实际上需要额外的存储系统，所以这里提供一种初始报价信息的传送是必要的。


### 受托回复

发布广播路径上的节点评估发布包，如果愿意接受存储委托，即可构建*受托包*响应。

发送者验证和回传上限等都与询问章节的回复包相同。

```go
(2)     Ver:        版本号。
(8)     ID:         原发布包中的ID，用于上级对应请求源。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Cipher:     用发布包里的 HPKE 公钥封装。
                    关联数据含发布 ID、Proof、WayOn、HopEnd。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
注：以下信息会用共享密钥加密
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(8)     Timestamp:  回复包的时间戳。
(1)     HopEnd:     抵达时的剩余跳数。
(32)    BaseToken:  基网联系口令。
                    当发布者去基网中搜寻 BaseID 联系时与对方核对。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    DataKey:    发布数据的完整 TID。
(32)    BaseID:     受托者在基网中的身份ID。
(32)    PunchID:    打洞协助节点的身份ID（STUN2 子网服务器），可选。
(~)     Bargain:    受托议价（可选）：
                    Name:       代币名称，可与 Deposit.Name 不同，≤32 字节
                    Amount:     期望支付数量
                    Receiver:   收款地址。仅参考，实际协商可能不同。≤64 字节
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra:      额外信息。可选，≤127 字节。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

发布包/受托包中的代币名称和金额只是一种意向表达，最终结果取决于发布者对受托回复的评估：是否愿意进一步联系协商。



## 数据传输

### 获取信息

询问者解密回复消息，获取相关的联系信息。

- BaseID 是数据源节点在基网的身份ID，可以通过基网获取对端的信息（IP:Port、SPKI、ECHConfig、NATT 等）。
- PunchID 如果回复者是 NAT 内网节点，此即为其所连 STUN2 服务子网的服务节点的ID，然后找到并请求其协助 UDP 打洞。

> **提示：**
> 节点的身份ID是跨应用一致的。基网 NodeID 只绑定节点的 IP，不含端口。
> STUN2 服务子网的节点也会连接基网，因此也可以从基网通过其身份ID（即 PunchID）找到。


### 传输数据

询问者尝试连接返回的数据源节点，通过文件分享方式，获取并组合分片，恢复完整的文档数据。

发现层只负责联系信息获取，文件的分享由一个单独的模块执行。就像 BitTorrent 一样，可以同时从多个源拉取数据。



## 安全性

### 末端延时

对于某些数据，可能有人不愿意它们被分享，因此大量部署监控节点，发现相关请求后立即响应，占据原路回传的头部位置，阻止真实回应。

因此这里设计一个「末端延时」的机制：

- 对于每一个询问，中转节点记下它抵达时的时间（本地时间）和包内的 WayEnd。
- 对于每个回复，验证通过后，至少暂存至其询问下发时间之后至少 **2~3** 秒才向上回传。
- 如果暂存期多个回复抵达，则随机抽选，此时先抵达的回复包没有优先性。

如果末端节点执行了该约束，回传路径中间的节点通常就不再需要延迟了，先抵达的回复先回传。注意，每一级的检查可确保该延迟被完成。

> **注记：**
> 2~3 秒大致是真实数据源查询本地数据需要的时间。

这样，如果攻击者想要完全阻断询问回复的抵达，就需要部署*十分充足*的节点或针对特定询问者围堵才能完成。



## 项目边界

- 节点发现由 [基网](https://github.com/cxio/p2p) 实现，驿站节点可以通过基网找到对方，包含 IP:Port、SPKI、ECHConfig 和 NAT 类型等信息。
- 提供打洞协助的 [STUN2 P2P 网络](https://github.com/cxio/stun2p) 是基网的一个服务子网，也可通过基网寻址，因此驿站节点可请求其帮助某个身份打洞。
- 每一个驿站节点也是基网的成员，只要驿站成网，基网就可用。如果 STUN2 不可用，则用能直连的数据源即可。
