# 详细设计

> **前提：**
> - 节点需要事先知道自身的 NAT 类型。
> - 出于隐私保护，数据包不附带明文位置信息（IP）。

伪代码格式约定：

- `(n)` 占用字节数，即 n bytes。
- `[n]` 占用比特位数，即 n bits。

部分字节数和比特位数只是一个示意值，主要表达一种设计意图。

下文里的重复哈希，`Hash` 都是 SHA-256 的前 20 字节。


## 数据标识

网络上的 `DataKey` 就是存储文档里的分片哈希树根 `TID`，固定 32 字节。

询问可以只带前缀，用来发现更长的键；回复里给出完整键，且前段必须与询问一致。探测、发布和补存都使用完整 TID。

文档数据本身的 `SHA3-512` 指纹只写在本地元信息里，不参与检索，也不是树根。


## 数据询问

应用节点创建「询问」消息包，其中包含目标数据标识，以及起始跳数。

数据询问遵循跳数递减规则，最高默认值**7**，每跳减一，减至**0**时终止转播。用户也可以设置更低的起跳数，但广播范围也会因此而缩减。剩余跳数只决定这次搜索的半径。数据紧缺与否看探测包的跳数，不看询问包。

在广播的路径中，拥有该数据的节点回复并停止转播，而没有该数据的节点将请求跳数减一后续传。前缀询问由持有更长键的节点回复。


### 询问包

```go
(2)     Ver:        版本号。
(8)     ID:         标识本次询问，用于回复包中对应其源请求。
(8)     Timestamp:  询问时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     DataKey:    数据键（≤32）。完整 TID，或它的前缀。
(~)     Size:       数据大小（字节数，0 值表示未知或忽略）。
(~)     HPKE:       算法标识 + 变长公钥。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Proof:      工作量证明。绑定下面的 WayEnd，以及分隔线以上的字段。
(1)     Hops:       剩余跳数，初始值 ≤7，最低到 0。逐跳改变，不进入证明。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下单向哈希链防止剩余跳数被抬高：
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(20)    WayOn:      路途哈希。逐跳改变，不进入证明。
(20)    WayEnd:     跳数终点。整路不变，必须进入证明。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

询问包为明文。但节点之间的通讯是加密的，避免第三方窥探。

广播的每跳扩散数为 `≤4`。节点可根据自身情况选择更少的扩散数，但只能低不能高，避免形成消息洪泛。邻居从基网的当前连接里选，驿站不另建一张覆盖图。

> **实现：**
> 中转节点应记住查询来源和这条询问的 WayEnd。回复要原路返回，回传时也要用 WayEnd 核对路途。

时间戳与本地时间相差超过 **2** 分钟的包直接丢弃，过旧或超前都一样。发布包、探测包相同。

重复的询问包不转发，重复判定用 Proof。已见 Proof 保留到它的时间窗结束，并设条数上限，满了就丢掉最旧的。发布与探测同样处理。

可变长字段和可选字段要有确定的空值编码，具体字节布局在规格中定义。


#### 单向哈希链

询问包携带 40 字节的单向哈希链，避免中继把剩余跳数改大、把广播拉长。

```go
// 源站。每次发包使用新的 32 字节 Seed，种子不外传。
WayOn = Hash(Seed)
WayEnd = WayOn
for i range Hops+1 {
    WayEnd = Hash(WayEnd)
}

// 接收方先验证，再决定回复或转发。
if Hops > 7 {
    return false
}
tmpOn = WayOn
for i range Hops+1 {
    tmpOn = Hash(tmpOn)
}
if tmpOn != WayEnd {
    return false
}

// Hops == 0：停止。否则转发前只走一步。
if Hops == 0 {
    return
}
Hops = Hops - 1
WayOn = Hash(WayOn)
```

初始跳数并不固定为 **7**，询问者可以根据自身需求（隐私）调整，但最大值为 **7**。

终点会绑定 Proof，中继可以在本地把链多走几步再转发（剩余跳数更小，广播更短），但无法换一条更长的链来实施放大。


### 阻滞器

节点可以任意构造目标键进行查询，如果目标是虚假的（没有真实数据对应），则消息会广播很远很宽，消耗带宽和资源。

这可能成为一种攻击方式，因此设计如下规则。

针对每一个连接的对端：

- **计数限制**：询问包上限 `10`（不同 `Proof`），超限后即暂停接受对端的新询问请求。
- **机会回归**：每收到一个询问包的有效回复则减 `1`（按 `Proof` 区分冲抵），这使得中转询问的机会回归。
- **重置计数**：计数持续 `20` 秒，时间结束后重置为 0，及时消除误判和阻滞。

这样，虚假的数据请求会被抑制在约 `2s/次` 的频率，且每个请求都要付出工作量。而正常的请求则问题不大。

> **进阶效果：**
> 数据稀疏区的广播速度会慢下来，而密集区则畅通无阻。虚假数据则会严重受阻。


### 工作量

每个询问都需要完成工作量计算，算法如下（示意）。

**通用部分：**

```go
import "github.com/cxio/equix-cgo/puzz"

// 命中率：6%
// 按当前普通 PC 标定，单核约 500 毫秒。
// 这是一个统一的固定配置，不可修改。否则不同客户端无法验证彼此。
threshold := puzz.FromProbability(0.06)

// 不可变字段。不含 Hops 与 WayOn。
// domainTag 查询包域标识：depots:Query@v1
baseInfo := domainTag ||
            Ver ||
            ID ||
            Timestamp ||
            DataKey ||
            Size ||
            HPKE ||
            WayEnd
```

**每查询求解：**

```go
// 求解：
// Hash256  哈希算法：SHA-256
// Rand16   工作量求解者寻找的16字节随机数，会作为证明的后半段
// solution 一个合法解，2*8 = 16字节
var Rand16, solution
for {
    // 每轮生成新的 Rand16
    Rand16 = ...
    solution, _ := threshold.Try( Hash256(baseInfo || Rand16) )
    if solution != nil {
        break
    }
}
Proof := solution || Rand16
```

**中转/末端验证：**

```go
// 验证解：
// 效率极高，适配现代PC，单核约 30~40 微秒。
Rand16 := Proof[16:]
solution := Proof[:16]
seed := Hash256( baseInfo || Rand16 )

return threshold.Accept( seed, solution )
```

中转节点先检查时间窗、工作量和哈希链，再看自己有没有目标数据。


### 响应回复

如果节点拥有目标数据，创建*回复包*响应。否则在跳数非零时，把跳数减一、`WayOn` 哈希一次后再转播。

返回的回复包会按询问广播的原路径逆向回传，逐级收敛回到查询者。

> **设计：**
> 原路回传既可以避免信息洪泛，也可以让询问者不必公开自己的位置（IP）。

如果数据源节点是受限 NAT 类型（`RC|P-RC|Sym-Like`），通常需要借助于 STUN2 服务子网协助打洞互连，所以会包含其所连接的 STUN2 子网服务节点的身份ID。

回复携带*抵达时*的 `WayOn` 与 `Hops`（记为 `HopEnd`）。回传路径上的中继用当初记下的 `WayEnd` 做同一种验证：把 `WayOn` 再哈希 `HopEnd+1` 次，结果必须等于 `WayEnd`。失败的回复丢弃：不占回传名额，阻滞计数也不回血。

注意，验证通过只说明回复者是这条链上的某一跳，其是否真有数据，需要等询问者抽取分片验证（匹配 TID）之后才晓得。


### 回复包

```go
(2)     Ver:        版本号。
(8)     ID:         原询问包中的ID，用于上级对应请求源。
(20)    WayOn:      抵达时的路途哈希。明文，供沿途核对。
(1)     HopEnd:     抵达时的剩余跳数。明文。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Cipher:     用询问包里的 HPKE 公钥封装。
                    关联数据含询问 ID、Proof、WayOn、HopEnd。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
注：以下信息会用共享密钥加密
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(8)     Timestamp:  回复包的时间戳。
(32)    HashSig:    基网私钥的签名哈希。
                    签名覆盖询问 ID、Proof、WayOn、HopEnd、BaseID。
                    当节点去基网中搜寻 BaseID 时才需要验证&核实。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    DataKey:    完整 TID。前缀询问时可以比询问中的键更长，前段必须相同。
(32)    BaseID:     回复者在基网中的身份ID。
(32)    PunchID:    打洞协助节点的身份ID（STUN2 子网服务器），可选。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra:      额外信息。可选，≤127 字节。
                    用例：
                    如果需要连接 STUN2 服务子网，可以是节点的身份识别号，
                    询问者借助于此识别号在 STUN2 子网中匹配它。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

询问者先按明文路途核对，再解密。然后用 `BaseID` 在基网中的 SPKI 验签；`DataKey` 必须是完整 TID，且前缀与询问一致。失败则丢弃。

> **设计：**
> 路途位置放在明文里，中继才核对得了。身份和如何联系仍在密文里。


### 回传策略

- 每个中转节点向上回传的回复包最多 **16** 个。这是强约束。
- 每个下级最多贡献 **4** 条。这也是强约束，避免一个下级灌满名额。

这样，对于发送询问的初始节点来说，如果它连接了 8 个节点发送询问，最多可收到 128 个回复（数据源不会对相同 Proof 查询重复响应）。到点后如何从已到达的回复里选取，见「末端延时」。



## 心跳探测

探测数据的存在性是一种特殊的请求，它不需要拥有数据的节点回复。探测包可同时携带 8 个 TID；持有者为对应 TID 写入首次命中的跳数，但只要还有 TID 未命中，整包就继续转播。

与询问包不同，探测包的起始跳数为零，遵循跳数**递增**的策略，最大跳数截止于 **15**。节点的转播扩散数与查询规则相同，去重同样通过 Proof 判断。

`Hops` 是整包在这一路已经走过的跳数，用来感知路径距离。每个 TID 是否已经遇到持有者由对应的 `HopClot` 单元表示。扇出不超过 4；某个 TID 的记录在较大跳数下仍为零，说明这条路径辐射区域内该数据比较稀缺。

任意节点都可以发出探测包，但需要付出工作量。心跳探测是一些愿意付出成本的公益节点或利益相关方的事。要扫的键来自可枚举的清单，如链上索引、节点自己的清单文件、机构组织的档案目录等。

另外，探测包还有频率的限制：**5次/秒**，每一个节点都会限制探测包的广播，避免洪泛。这是一个综合平均值，实现可采用令牌桶形式，包容多个发布者同时高频发布时可能的峰值流量，比如 *30~50次/秒* 的桶深。

> **设计：**
> 探测包没有签名认证机制，因此用工作量和频率来对抗可能的攻击。


### 探测包

```go
(2)     Ver:        版本号。
(8)     Timestamp:  起始时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(256)   Keys:       数据键集，TID * 8。
(4)     HopClot:    跳数记录，以 4 Bit 为单元，可存 8 个值。
                    与 Keys 中的各 TID 一一对应。
                    值为首个存在该数据的节点的跳数（已完成 +1），由该节点设置。
                    后续节点无论是否拥有相同数据，都不再修改相应位。
                    当所有单元都被赋值（非零）时终止转播。
                    跳数抵达上限 15 依然没有数据时，终止转播（值依然为零）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Proof:      探测工作量证明。绑定字段详见下文。
(1)     Hops:       跳数累计，初始值 0，首跳为 1，最高 15。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下单向哈希链防止 Hops 被改小：
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(20)    WayOn:      路途哈希。不进入证明。
(20)    WayEnd:     跳数终点。必须进入证明。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

探测包为明文，无加密。合计字节数不超过 350 bytes，因此探测是轻量的。


### 单向哈希链

```go
// 源站。Seed 同样每次重新抽取，不外传。
WayOn = Hash(Seed)
WayEnd = WayOn
for i range 16 {
    WayEnd = Hash(WayEnd)
}
Hops = 0

// 接收：
if Hops > 15 {
    return false
}
tmp = WayOn
for i range 16-Hops {
    tmp = Hash(tmp)
}
if tmp != WayEnd {
    return false
}

// 已经走到 15：停止。否则只前进一跳。
if Hops == 15 {
    return
}
Hops = Hops + 1
WayOn = Hash(WayOn)
```

不良中继可把链多走几步，这会让 `Hops` 变大，剩下的路程变短。紧缺读数因此会偏高，但影响只作用于该单条路径。


### 探测包工作量

探测包的工作量设计与询问包类似，只是绑定的字段不同。

```go
// 基础信息：
// 探测包里的不可变字段值。
// domainTag 探测包域标识：depots:Probing@v1
baseInfo := domainTag ||
            Ver ||
            Timestamp ||
            Keys ||
            WayEnd
```

其它求解和工作量验证逻辑与「询问包」章节相同。


### 补充储备

节点根据收到的探测包进行存储评估，评估是复杂的，需要考虑多种因素。详见 [存储策略](存储策略.md) 设计。

如果节点最终决定补存，即发送询问请求，查询并获取数据。



## 数据发布

新数据的发布采用专用的**发布包**请求，结构与询问包类似，但包含数据的元信息（非可选）。哈希链、时间窗、去重和阻滞器都与询问包相同。

`Deposit` 与受托回复里的 `Bargain` 只是报价捎带，没有更多的业务逻辑。


### 发布包

```go
(2)     Ver:        版本号。
(8)     ID:         标识本次发布，用于回复包中对应其源请求。
(8)     Timestamp:  发布时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    DataKey:    完整 TID。
(~)     MetaInfo:   数据元信息：
                    Kind:     种类，2字节（1+1）
                    Title:    数据名称/标题，≤127 字节
                    Summary:  内容摘要。≤500 字节
                    Size:     数据大小（字节数）
                    License:  许可证名称，≤64 字节
(~)     HPKE:       算法标识 + 变长公钥。
(~)     Deposit:    寄存激励（可选）：
                    Name:     代币名称（区块链，如 Bitcoin），≤32 字节
                    Amount:   预期支付数量（报价）
                    Payfrom:  支付地址。仅参考用途，实际可能不同，≤64 字节
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Proof:      工作量证明。绑定 WayEnd 以及以上字段。
(1)     Hops:       剩余跳数，初始值 ≤7，最低到 0。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下为单向哈希链（算法同询问包）：
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(20)    WayOn:      路途哈希。
(20)    WayEnd:     跳数终点。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

发布包包含可选的区块链代币激励（通常为到期兑付合约）条件。

> **注：**
> 发布包也有回复（受托回复），因此也可适用阻滞器机制设计。


### 发布包工作量

发布包的工作量与询问包类似，只是绑定字段不同，难度相同。

```go
// 基础信息：
// 发布包里的不可变字段值。
// domainTag  查询用域标识：depots:Publish@v1
baseInfo := domainTag ||
            Ver ||
            ID ||
            Timestamp ||
            DataKey ||
            MetaInfo ||
            HPKE ||
            Deposit ||
            WayEnd
```

其它求解和工作量验证逻辑与「询问包」章节相同。源站同样先确定 `WayEnd`，再求解 Proof。


### 关于寄存激励

与 Filecoin 严格的存储验证/激励不同，这是一种松散的自由合约形式。发布者向网络发布数据请求外部存储，有意愿者回应，双方联系后协商寄存合约。合约通常是一种「到期兑付」脚本，也不限制代币类型。

注意，这里只提供基本报价信息的传送，不负责任何实际的交易或约束。

因为链上的附件通常只保存附件ID，实际上需要额外的存储，所以这里提供一种初始报价信息的传送是必要的。


### 受托回复

发布广播路径上的节点评估发布包，如果愿意接受存储委托，即可构建*受托包*响应。路途核对、发送者认证和回传上限都与询问的回复包相同。

```go
(2)     Ver:        版本号。
(8)     ID:         原发布包中的ID，用于上级对应请求源。
(20)    WayOn:      抵达时的路途哈希。明文。
(1)     HopEnd:     抵达时的剩余跳数。明文。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Cipher:     用发布包里的 HPKE 公钥封装。
                    关联数据含发布 ID、Proof、WayOn、HopEnd。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
注：以下信息会用共享密钥加密
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(8)     Timestamp:  回复包的时间戳。
(32)    HashSig:    基网私钥的签名哈希。
                    覆盖发布 ID、Proof、WayOn、HopEnd、BaseID。
                    当发布者去基网中搜寻 BaseID 联系时才需要验证&核实。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    DataKey:    发布数据的完整 TID。
(32)    BaseID:     受托者在基网中的身份ID。
(32)    PunchID:    打洞协助节点的身份ID（STUN2 子网服务器），可选。
(~)     Bargain:    受托议价（可选）：
                    Name:       代币名称，可与 Deposit.Name 不同，≤32 字节
                    Amount:     期望支付数量
                    Receiver:   收款地址。仅参考，实际协商可能不同。≤64 字节
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra:      额外信息。可选，≤127 字节。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

发布包/受托包中的代币名称和金额只是一种意向表达，最终结果取决于发布者对受托回复的评估：是否会进一步联系协商。



## 数据传输

### 获取信息

询问者先核对明文路途，再解密、验签，然后才使用里面的联系信息。

- BaseID 是数据源节点在基网的身份ID，因此可以通过基网获取对端的联系信息（IP:Port、SPKI、ECHConfig、NATT 等）。
- PunchID 如果回复者是 NAT 内网节点，此ID即为其所连 STUN2 服务子网的服务节点ID。然后就可以请求该节点进行 UDP 打洞协助。

> **提示：**
> 节点的身份ID是跨应用一致的。基网 NodeID 只绑定节点的 IP，不含端口。
> STUN2 服务子网的节点也会连接基网，因此也可以从基网通过其身份ID（即 PunchID）找到。


### 传输数据

询问者只连接通过核对的源。数据按分片传输，分片挂在 TID 这棵哈希树上，对不上树路径的分片丢弃。可以同时从多个源拉取。

打洞失败就放弃这个源，换下一条回复。发现层不搬运文件字节，也不另做数据中继。



## 安全性

### 末端延时

对于某些数据，可能有人不愿意它们被分享，因此大量部署监控节点，发现相关请求后立即响应，占据原路回传的头部位置，阻止真实回应。

因此这里设计这一机制：

- 对于每一个询问，中转节点记下它的时间戳和 WayEnd。
- 路途核对失败的回复立即丢弃。
- 通过对的回复先收着，至少比询问时间晚 **2~3** 秒再向上送。
- 到点后，在本跳已经收齐的合格回复里抽取，直到 16 条的上限；每个下级最多留 4 条。先到的包没有优先权。

这种末端延时由见到回复的节点实施，通常就是回复者的上一级（回传的源节点）完成。

对于回传路径的中间节点来说，因为末端延时已经完成，所以此时节点有一个自己的暂存时间，收集下级的回复包，到点后抽取最多16个包回传。

> **注记：**
> 2~3 秒大致是真实数据源查询本地数据需要的时间。

这样，如果攻击者想要完全阻断询问回复的抵达，就需要部署*十分充足*的节点或针对特定询问者围堵才能完成。



## 项目边界

- 节点发现由 [基网](https://github.com/cxio/p2p) 实现，驿站节点可以通过基网找到对方。节点ID是跨应用一致的。基网至少要能按 NodeID 查到 IP:Port、SPKI、ECHConfig 和 NAT 类型。
- 提供打洞协助的 [STUN2 P2P 网络](https://github.com/cxio/stun2p) 是基网的一个服务子网，也可以通过基网寻址。驿站按服务节点 ID 请求它帮助某个身份打洞。
- 基网不可用时，驿站不对外询问和发布，只保留本地存档。STUN2 不可用时，跳过需要打洞的源，能直连的回复仍然可用。
